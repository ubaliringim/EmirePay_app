Overview & Information Architecture

The current build (see lib/screens/more/more_screen.dart) ships a static, UI-only version of this menu: identity header, three grouped lists, and a logout row. This spec turns each row into a fully specified product surface — the destination screen(s), the data contract, and the operational concerns (audit, fraud, notifications) a fintech regulator and a support desk will both ask about on day one.

Design Tokens Referenced Throughout

  • account.kycLevel drives every gated action (limits, card issuance, referral payout).
  • All destructive/irreversible actions (remove bank, delete card, logout-all) require PIN or biometric step-up, not just a confirm dialog.
  • Every write endpoint below returns a standard envelope: {status, code, message, data} and every mutating call is idempotent via Idempotency-Key header.
  • All screens ship a skeleton-loader state, not a spinner, for list/detail views > 300ms.
01

Profile

Profile is the identity record underpinning KYC tier, transaction limits, and dispute resolution. It is read-heavy (users check their account number and KYC level constantly) and low-frequency-write (edits are rare, verification is one-time per channel). Split into four screens so the identity edit surface — the one with regulatory weight — isn't buried inside a settings list.

Account · Profile

Profile Overview

Read-only summary of who the account belongs to, its verification tier, and system identifiers.

Purpose

Give the user one place to confirm their identity is correctly on file and to see, at a glance, how "verified" their account is — because KYC level directly gates how much money they can move.

User Story

As a user, I want to see my full profile, verification status, and account identifiers, so I know what I'm allowed to do on this account and where to look up my account number for a bank transfer.

Verify Email / Verify Phone (OTP)

Shared OTP verification component, reused by Profile, Security, and Cards & Banks wherever a channel needs proof of ownership.

Purpose

Confirm the user actually controls the email/phone before it's trusted for password reset, transaction alerts, or dispute contact.

User Story

As a user, I want a fast, obvious way to confirm a 6-digit code so changing my contact details doesn't feel like extra homework.

Screen Layout

┌ ← Verify your email ─────────────┐
│  We sent a 6-digit code to         │
│  m•••••u@gmail.com                 │
│                                     │
│   [_] [_] [_] [_] [_] [_]          │
│                                     │
│  Resend code in 0:47               │
│  Didn't get it? Use phone instead  │
│                                     │
│  [          Verify           ]     │
└─────────────────────────────────────┘

Validation

  • 6 numeric digits, auto-submits on 6th digit entered
  • Code expires in 5 minutes; max 5 attempts per code before lockout
  • Resend cooldown 60s, capped at 5 resends per hour per channel

API Calls

CallMethod
/v1/otp/send {channel, purpose}POST
/v1/otp/verify {channel, code, purpose}POST

Error / Success

  • Wrong code: shake animation + "Incorrect code, N attempts left"
  • Expired: "This code has expired — resend"
  • Locked out: "Too many attempts — try again in 15 min", channel locked
  • Success: checkmark animation → toast "Email verified" → pop back

Edge Cases

  • Purpose-bound codes: an email-verify OTP cannot be replayed to confirm a PIN reset (server validates purpose)
  • User already verified via another device mid-flow → poll/refresh shows "Already verified" success state

Security Considerations

  • Rate-limited per user and per device/IP to block enumeration/brute force
  • OTPs are single-use, invalidated immediately on success or on a new code being requested
  • All OTP attempts (success/fail) logged with masked destination, never the raw code

Notifications & Audit

Email/SMS: "Your EmirePay code is 482913, valid for 5 minutes." Audit: otp.sent, otp.verified, otp.failed, otp.locked.

This is the module a regulator, an auditor, and a fraud victim will all scrutinize first. Every screen here assumes hostile conditions: a stolen phone, a SIM-swap attempt, a phishing OTP request. Account · Security

Change Transaction PIN

4–6 digit PIN used to authorize every payment, transfer, and bill.

Purpose

Let a user rotate their transaction PIN on their own schedule (e.g. after sharing a phone, or on a security scare) without needing support intervention.

User Story

As a user, I want to change my 4-digit PIN by confirming my current one, so no one who glimpsed my old PIN can keep transacting on my account.

Screen Layout

Step 1/3            Step 2/3            Step 3/3
Enter current PIN    Enter new PIN       Confirm new PIN
[● ● ● ●]            [_ _ _ _]           [_ _ _ _]
                      Must differ from
                      last 3 PINs

Validation Rules

  • Exactly 4 digits (6-digit optional per account settings)
  • Reject sequential (1234, 4321) and repeated (1111) PINs
  • Cannot match current PIN or last 3 previous PINs (hashed comparison, server-side)
  • Cannot equal 4 digits of the user's own DOB or phone number tail
  • Confirm step must exactly match new PIN, else "PINs don't match, try again" and both fields clear

API Calls

CallMethod
/v1/security/pin/verifyPOST — validates current PIN before allowing step 2
/v1/security/pin/changePOST {currentPin, newPin}, both sent over TLS, never logged

Error States

  • Wrong current PIN → "Incorrect PIN, N attempts left" (3 attempts → 30 min lockout → email alert)
  • Weak new PIN → inline rule violation list, submit disabled until resolved
  • Network failure mid-change → "Change not saved — try again", old PIN remains active

Success State

Checkmark animation, toast "PIN changed successfully", auto-logout of all other sessions, push+email notification sent, return to Security Hub.

Edge Cases

  • 3 consecutive wrong current-PIN attempts → PIN locked, forces Forgot PIN flow (BVN/OTP-based reset) instead of retry
  • User changes PIN, then immediately tries a transaction on a second device with the old PIN cached → server rejects, forces re-auth

Security Considerations

  • PIN is hashed (Argon2id) server-side, never stored or transmitted in plaintext beyond the TLS session
  • Keypad uses randomized digit layout option to defeat shoulder-surfing (configurable)
  • Rate limiting: 3 fails → 30 min lock; 3 lockouts in 24h → account flagged for manual review

Database

user_credentials(user_id, pin_hash, pin_updated_at, pin_fail_count, pin_locked_until, pin_history[] hashed)

Notifications / Audit

Push+Email+SMS: "Your transaction PIN was changed just now. Not you? Contact support immediately." Audit: pin.changed, pin.change_failed, pin.locked.

Account · Security

Forgot / Reset PIN

Recovery path when the current PIN is unknown or locked — deliberately slower and more heavily verified than a normal change.

Purpose

Restore transacting ability to the legitimate owner while making the flow expensive enough that an attacker holding only the phone (no BVN/ID) can't reset the PIN and drain the wallet.

User Story

As a user who forgot my PIN, I want to reset it using identity verification I already completed at signup, without having to visit a branch.

Screen Layout

Step 1  Verify identity
  ( ) OTP to registered phone
  ( ) OTP to registered email
  ( ) BVN re-verification (if steps 1–2 fail)
Step 2  Enter new PIN
Step 3  Confirm new PIN
Step 4  Success — cooldown notice

Validation / Business Logic

  • Requires two independent verification factors, not one (e.g. OTP + last-4-of-BVN, or OTP + selfie liveness match against BVN photo)
  • New PIN follows the same strength rules as Change PIN
  • 24-hour transaction limit reduction (e.g. capped at ₦50,000) applied automatically for 24h after any PIN reset, regardless of amount previously allowed — standard fraud-mitigation cooldown

API Calls

CallMethod
/v1/security/pin/reset/initiatePOST
/v1/otp/verifyPOST (reused, purpose=pin_reset)
/v1/security/pin/reset/completePOST {newPin}

Error / Success

  • Identity verification fails twice → escalate to Help Center ticket with manual agent review (no further in-app retry same day)
  • Success → toast "PIN reset. A 24h security limit applies to keep your account safe." + forced logout of other sessions

Security Considerations

This is the single highest-value target for social engineering in the whole app — every step is logged with device fingerprint + IP + geolocation, and a reset from a never-seen-before device additionally requires a 1-hour delay ("cool-off") before completion, communicated clearly in-flow.

Notifications / Audit

Immediate push+email+SMS on initiation and completion (two separate alerts). Audit: pin.reset_initiated, pin.reset_completed, pin.reset_denied.

Account · Security

Change / Forgot Password

Login credential, separate from the transaction PIN.

Purpose & User Story

As a user, I want to change my login password proactively, or recover it via email/SMS if I forget it, without that action alone letting anyone move money (PIN stays separate).

Screen Layout

Change Password           Forgot Password
Current password [••••]   Enter registered email
New password      [    ]  → OTP / reset link sent
Confirm password  [    ]  → Set new password
Strength: ▓▓▓░░ Good      → Confirm password

Validation Rules

  • Min 10 characters, at least 1 upper, 1 lower, 1 number, 1 symbol
  • Rejected against a common-password/breached-password list (e.g. HaveIBeenPwned range API)
  • Cannot reuse last 5 passwords
  • Live strength meter (weak/fair/good/strong) as the user types

API Calls

CallMethod
/v1/auth/password/changePOST (authenticated)
/v1/auth/password/forgotPOST {email} — always 200, never reveals if email exists
/v1/auth/password/resetPOST {token/otp, newPassword}

Error / Success

  • Wrong current password → "Incorrect password" (5 fails → 15 min lock)
  • Reset link expired (15 min TTL) → "This link has expired, request a new one"
  • Success → all sessions except current logged out, confirmation email sent, toast "Password updated"

Security

  • Bcrypt/Argon2id hashing, per-user salt
  • Forgot-password response is identical whether or not the email exists (anti-enumeration)
  • Reset tokens are single-use, invalidated on password change

Logout Flow

Deliberately two-tap, with an explicit choice between this device and everywhere.

Purpose & User Story

As a user, I want to sign out of just this phone normally, but have a fast way to sign out everywhere if I suspect my account is compromised.

Screen Layout

┌  Log out of EmirePay?  ┐
│  You'll need your PIN or   │
│  password to log back in.  │
│                             │
│  [   Log out this device  ]│
│  [   Log out all devices  ]│
│  [        Cancel          ]│
└─────────────────────────────┘

Business Logic

  1. Confirm sheet from tapping "Log Out" on More
  2. Server invalidates the access/refresh token pair for the chosen scope (this device, or all devices)
  3. Client clears in-memory state, cached API responses, and secure-storage tokens
  4. Local biometric binding is not removed on a normal logout (kept for fast re-login), but push token is deregistered
  5. Redirects to Sign In screen

API Calls

CallMethod
/v1/auth/logoutPOST {scope: "device"|"all"}

Loading / Error / Success

  • Loading: buttons show inline spinner, sheet non-dismissible mid-request
  • Error: network failure → local session is cleared anyway (client always trusts local logout to avoid trapping a user offline), server-side revoke retried in background
  • Success: immediate redirect to Sign In, no toast (destination is the confirmation)

Edge Cases

  • Logout triggered by the security fraud engine (forced) → same flow, but with a mandatory explanatory screen before Sign In, not a silent bounce
  • Pending unsynced local data (rare, e.g. a queued feedback draft) → discarded on logout, no draft persistence across accounts

Security Considerations

Refresh tokens are revoked server-side, not just discarded client-side, so a captured token can't be replayed after logout. "Log out all devices" is identical in effect to Security Hub's "Log out other devices" plus this device.

Signature User Journey — "I Lost My Phone"

Chosen because it touches nine of the eleven modules and is the highest-stakes path through More.

1. New phone → Sign In → Forgot Password (email OTP)
2. Signed in → Security Hub → risk banner "new device"
3. → Trusted Devices → remove old phone
4. → Login Sessions → confirm no unrecognized activity
5. → Change Transaction PIN → new PIN set
6. → Two-Factor Authentication → re-enroll TOTP (old backup codes invalidated)
7. → Biometric Login → enroll on new device
8. → Cards & Banks → Card Detail → confirm no unfamiliar card
9. → Help Center → Raise Ticket ("lost device") for the paper trail
Outcome: account fully re-secured in one continuous flow, no support agent required.

11 · Security Checklist

FinTech Security Checklist

  • ☑ PCI-DSS SAQ-A scope maintained — raw PAN/CVV never touch app backend, tokenized client-side
  • ☑ PIN/password hashed with Argon2id, per-user salt, never logged in plaintext anywhere (app logs, crash reports, analytics)
  • ☑ All destructive/high-value actions require step-up auth (PIN or biometric), not just a confirm dialog
  • ☑ Rate limiting + progressive lockout on PIN, password, and OTP attempts
  • ☑ OTPs are purpose-bound, single-use, short-TTL, and rate-limited per user and per device/IP
  • ☑ Refresh tokens revoked server-side on logout, not just discarded client-side
  • ☑ Sensitive screens (PIN entry, card reveal, security hub) block screenshots/screen-recording
  • ☑ Anti-enumeration on forgot-password/forgot-email flows (identical response whether account exists or not)
  • ☑ Biometric match is on-device only; server never receives raw biometric data
  • ☑ Every credential/limit/device change fires a real-time alert on a channel the attacker doesn't control (i.e. not just in-app)
  • ☑ Full audit trail (who, what, when, from where) for every mutating endpoint in this document
  • ☑ AML controls: bank-name match on linking, self-referral fraud detection, KYC-tiered limits enforced server-side (never trust client-sent limits)
12–14 · UX, Accessibility & Mobile Guidelines

Craft Standards

UX Best Practices

  • Never make a user re-enter data lost to a background/interrupt (draft state persists locally)
  • Every irreversible action gets a confirm step that names the consequence, not a generic "Are you sure?"
  • Toasts confirm state changes; full-screen success only for flows the user waited on (OTP, card verify)
  • Errors are written in plain language with a next step, never a raw error code alone

Accessibility Checklist

  • ☑ All tap targets ≥ 44×44dp; PIN keypad keys ≥ 48dp
  • ☑ Color is never the only status signal (icon + text pairs every pill/badge)
  • ☑ Screen reader labels on every icon-only button (copy, freeze, remove)
  • ☑ Minimum 4.5:1 text contrast in both themes; verified against the token palette above
  • ☑ Form errors announced via live region, not just visual inline text
  • ☑ Biometric flows always offer a fully accessible PIN fallback path

Mobile Design Guidelines

  • Destructive actions bottom-sheet on mobile (thumb-reachable), never a top-anchored modal
  • Numeric keypads (PIN, OTP, card number) use the platform-native numeric keyboard, not a custom one, except the randomized-layout security keypad
  • Sticky primary actions (Save, Submit) stay above the keyboard inset on all form screens
  • Pull-to-refresh on every list/detail screen backed by a GET (Overview, Devices, Sessions, Tickets, Referral History)

16–18 · Requirements & PRD Summary

Functional / Non-Functional Requirements

Functional Requirements (sample)

  • FR-1 Users must be able to view and edit non-immutable profile fields
  • FR-2 Legal name/DOB changes must route through a compliance-reviewed correction request
  • FR-3 Transaction PIN and login password must be independently changeable
  • FR-4 Every bank/card link must be ownership-verified before use
  • FR-5 Notification preferences must be settable per category and per channel, with security/transaction alerts non-disableable
  • FR-6 Users must be able to see and revoke access from any device

Non-Functional Requirements

  • NFR-1 P95 API latency < 400ms for all GET endpoints in this module
  • NFR-2 99.9% availability for auth/security endpoints (PIN, password, OTP)
  • NFR-3 All PII at rest encrypted (AES-256); secrets in a managed KMS, not app config
  • NFR-4 Full audit log retained ≥ 7 years (NDPR/CBN record-keeping)
  • NFR-5 Offline-tolerant reads (last-known-good cache) for Profile Overview and About

PRD Summary

Problem: the More section is currently a static menu with no destinations. Goal: ship the eleven screens above so users can self-serve identity management, security hardening, payment-instrument control, and support — without contacting an agent for anything that doesn't require human judgment. Success metric: support ticket volume for "how do I…" categories drops ≥ 40% within one quarter of launch; self-serve PIN/password reset completion rate ≥ 90%.
